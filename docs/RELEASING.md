# 发布流程

> 发布是不可逆的公开动作：装到用户机器上的版本会长期存在。
> 一次「一眼可见的低级错误」对公信力的伤害，远大于延迟一周发布。

## 硬性门禁（缺一不可）

1. CI 全绿：三平台 fmt / clippy / test、Desktop check、MongoDB 集成测试
2. 发布候选**在真实应用里**走一遍下方冒烟清单（build 通过不算验证）
3. 冒烟在 `pnpm tauri dev` 或本地安装包上完成，逐项记录结果
4. 多个问题**合并为一次发布**；不要看到一个修一个、当天连发 patch

## 冒烟清单（每次发布逐项打勾）

| 入口 | 检查点 |
| --- | --- |
| 主界面连接表单 | 每种数据库类型都能选中；选 SQLite 出现文件选择；选 Oracle 出现服务名；选 MongoDB 填连接串时端口 / 账号 / 密码置灰 |
| 连接管理 | 新增连接：每种类型都能选中；保存后重新打开，类型与字段正确回显 |
| 导出 | Excel 与 Markdown 各导一次，打开确认表结构、目录正常 |
| MongoDB 专项 | 有 validator 与无 validator 的集合各一个；确认表级来源标注与采样覆盖率 |
| CLI | `dbs --help`、`dbs export --help`，确认 `--driver` 列表与实际支持一致 |

## 为什么要有这道门禁

**0.5.0 的教训**：`DB_TYPES` 在 `App.tsx` 与 `ConnectionManager.tsx` 各有一份，
加 MongoDB 时只改了一处。`pnpm build` 通过、CI 通过，但用户打开「连接管理」
第一眼就发现看不到 MongoDB——半小时后被迫发 0.5.1 擦屁股。

自动化能防的：列表是否单一定义、构建是否通过、测试是否全绿。
自动化防不了的：**入口是否真的点得通**——这一项必须人工逐项走。

## 版本节奏

- patch 只包含已合并的问题修复，且尽量间隔一天观察
- 同一天连发两个版本，说明前一个版本没验证充分；停下来补验证，而不是继续发
- 发布前把「这次改了什么、影响哪些入口」写在 PR / 提交里，冒烟按入口逐条覆盖

## 防漂移的自动检查

`desktop.yml` 会检查 `src` 下不存在本地定义的 `DB_TYPES`：
数据库类型列表必须来自 `src/dbTypes.ts`，禁止在组件内复制。
