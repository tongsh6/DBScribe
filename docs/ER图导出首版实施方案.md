# ER 图导出首版实施方案

本方案说明从数据库目录到 ER 图的处理过程。关系推断先回答“哪些字段值得比较”，再回答“已有材料是否足以选定一个目标”。这两步分开，才能在扩大异名关系发现范围的同时，保留对不确定关系暂缓判断的能力。[首版需求](ER图导出首版需求.md)

## 一、现有代码与职责边界

| 模块 | 现有能力 | 拟承担的职责 |
| --- | --- | --- |
| [dbs-db 元数据读取](../crates/dbs-db/src/lib.rs) | 按驱动读取基础表、列、索引与外键 | 读取原始目录，保留方言特有的有效性、顺序和类型信息，区分缺失、不可读和确实不存在。可选视图证据单独读取。 |
| [dbs-core 模型](../crates/dbs-core/src/model.rs) | `TableInfo` 保留 schema、字段、索引和已声明外键 | 在拟新增的 `er` 模块中维护证据、候选及裁决。业务推断单独存放，避免改变 `foreign_keys` 对已有调用方的含义。 |
| [dbs-doc 导出](../crates/dbs-doc/src/lib.rs) | 文档导出会过滤、排序并可能调整显示表名；[Markdown 关系图](../crates/dbs-doc/src/markdown.rs)从外键构建 | SVG 接收已裁决并按选表截取的节点和边。原始端点身份由推断层提供。 |
| [CLI](../crates/dbs-cli/src/main.rs) 与[桌面端](../apps/desktop/src/App.tsx) | 共用 Rust 后端。桌面[表列表与导出命令](../apps/desktop/src-tauri/src/commands.rs)当前按裸表名传递和过滤 | 共用一次推断结果。把限定表身份贯通列表、勾选、字段详情和导出，以便区分不同 schema 下的同名表。 |

## 二、输入与中间结果

**目录身份。** 表以原始数据库上下文、schema 或 owner、表名标识；字段在表内保留原名。名称归一仅用于匹配。端点由表身份与有序字段组构成，关系保留两端逐列映射、方向、角色与适用条件。复合键以完整键定义为单位，不能将成员列各自视作唯一键。

**键与类型。** 驱动报告主键或唯一键的真实键位顺序、是否全表有效、是否为普通列，以及判断类型可比性所需的原始属性。部分唯一、过滤索引、包含列和表达式须按方言区分。无法取得的信息标为未知。当前需要注意 [PostgreSQL 索引查询](../crates/dbs-db/src/postgres.rs)按表列序排序、[SQLite 索引读取](../crates/dbs-db/src/sqlite.rs)对 origin 和 partial 的区分，以及 [Oracle](../crates/dbs-db/src/oracle.rs) 和[达梦](../crates/dbs-db/src/dameng.rs)外键目标 owner 的保留。

**证据。** 每条观察记录其原始对象和位置、可核对的原始描述、作用域、涉及的角色或字段，以及可追溯的上游来源。派生出的分词、别名和视图投影保留来源链。每个候选分别记录结构检查、业务指向、反证和缺失信息；裁决附带采用的依据和暂缓原因。

## 三、从元数据提取业务含义

**MongoDB 的目录证据。** 读取当前库的集合规格、验证规则、原始索引选项与已保存的视图定义。节点取基础集合，嵌入字段保留路径；识别键时区分普通完整唯一键、稀疏索引、部分索引和可能的数组索引。只有可确定的标量 BSON 类型参与类型比较，集合中的 `_id` 不假定为 `ObjectId`。列表和 ER 命令均不需要读取业务文档。

对于能静态还原的直接 `$lookup`，来源为视图基础集合的 `localField`，目标为 `from` 集合的 `foreignField`，保留视图出处。这个方向来自查询定义，不需要以数据库外键或目标唯一性解释。查询边与同端点推断边合并时以查询出处展示。对存在竞争的普通业务指向保留候选；复杂管道和不可定位的字段不产生无条件查询线。MongoDB 连接作用域只保存集群地址与库名。[MongoDB 对 $lookup 的定义](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/)

### 先读目标定义，再解释来源字段

先从库里实际存在的表、完整键和说明建立本库词表，再用它解析字段。首版内置的是语言与命名规则：标识符分词、限定路径、引用或归属表达、否定、时态和条件范围。项目里的业务名词和别名必须有目录材料可追溯。两个词在相邻位置出现、经常同现或字面相近，可以作为检索线索，不能据此把它们登记为同一个业务对象。

保留原始文本及位置。英文标识符按词边界归一，中文描述按分句识别谓词及其支配的短语，再匹配本库词表；限定表名和字段名按方言的标识符规则解析。优先保留完整短语；不同切分会指向不同实体、角色或键时，保留歧义。否定、历史状态、外部归属和条件要附到它们实际修饰的陈述，不能因为同一注释里出现了某个词，就否决整段文字。

| 要识别的含义 | 提取规则 | 判断边界 |
| --- | --- | --- |
| 业务实体 | 表名、表说明中明确命名的对象构成实体称谓；显式别称指向同一限定表身份。 | 同一称谓可指向多张表。表说明可以限定上下文，不能为每个字段补出同一个引用目标。 |
| 业务角色 | 从来源字段的角色修饰语、归属表达或引用谓词中，提取该字段在当前记录中承担的职责，同时记录角色属于哪个对象、适用于什么范围。 | 对象类别只回答“涉及谁”，不能填充“以什么身份参与”。存在多种语法归属或只有实体称谓时，角色记为未知。 |
| 键的用途 | 先按约束识别完整目标键，再用键名、键列说明及所属表定义提取标识对象、标识方式和适用范围。来源字段也按相同维度提取其所保存的标识。 | 主键或唯一键证明结构资格。内部标识、业务编码、外部标识属于不同用途；自增、类型或长度不能单独确定业务用途。目标有多个唯一键时，不能默认挑主键。 |
| 引用意图 | 区分当前明确指向、仅描述内容、明确否定、历史陈述和有条件指向。记录谓词两端及其限定范围。 | 只有对当前来源成立的肯定陈述才支持无条件方向。角色词本身不能补出引用意图。 |

提取时先读能直接定位的限定标识符，再标出本库已知的实体称谓与键用途词，然后解析它们在分句中的关系。引用谓词所支配的对象短语用于识别目标；修饰来源字段、说明其职责的短语才可绑定为角色。名称拆分后剩余的词不能直接填作角色。若一个修饰语可以归属到两个对象，两种解释均保留，不能用最长匹配强选其一。

键用途分别记录**标识哪个对象、采用何种标识、由哪个范围定义、是否依赖其他字段**。命名只提供词义线索，约束只提供键的结构；字段说明中有明确表述的维度才能作为业务判断的依据。未提及的维度保留未知，不推定为与目标一致。某个未知维度只有在会改变目标或键的选择时才阻止自动判断。

每个提取项区分原文明确表达、由命名拆得和无法确定，并分别保留当前字段、所属表和其他对象的出处。

### 建立可用的项目内角色映射

在候选裁决前单独读取直接材料，建立“业务域、角色、标识用途、条件 → 完整目标端点”的映射。可作为依据的材料包括明确写出原始端点的当前引用，以及可解析回两端原始列、且方向、业务角色和适用条件另有原始材料支持的视图比较。等值比较自身没有方向。投影、别名或表达式的列来源无法还原时，只保留可说明的部分。

同域需要有明确的业务归属。物理 schema、表名前缀及相邻表只供检索。相同角色在不同作用域可以有不同映射，因此映射表允许一个检索键返回多个目标。只从原始材料建立这张表，并在本次运行中冻结；后续生成的候选和自动边都不能回流。

## 四、异名候选如何产生，证据怎样去重

### 先求候选并集，再逐项核对

对每个来源字段组，分别执行下列查找：

1. **精确端点。** 解析限定字段引用，或从可读视图追溯真实列对；保留它来自何种陈述、是否有方向及条件。
2. **实体与键用途。** 先按来源描述查可能的实体，再在每个实体内按标识用途查完整键。实体明确、键用途不明时，保留仍合理的键，不能因为其中一个是主键就结束查找。只有通用标识词或类型相同、没有实体或角色线索时，不展开全库组合。
3. **角色迁移。** 用当前字段自身的业务域、角色和标识用途查冻结的角色映射。已知范围不相容时排除该映射；范围缺失时，有明确角色线索可以召回，但暂不满足自动迁移条件。
4. **常规命名。** 实体词和键名的完整命名约定作为独立查找路径保留。形态归一、缩写或局部词重合只承担其能够支持的那部分判断。

各路径取并集，避免先按同名过滤而丢失异名目标。以来源字段组、目标完整键、逐列配对、方向、角色和条件合并重复候选，保留所有原始出处。已知的复合目标键驱动列配对：每个键位都要有来源列，且对应方式唯一。缺列或配对有歧义时不能拆成单列关系。只在角色、方向和适用条件相同的来源字段组内比较互斥目标。

### 独立性按“要证明的判断”计算

先写清两份材料各自要证明什么：字段表达哪种角色、该角色在此域指向哪个键、该键是否结构有效。不同材料重复证明结构有效，不能弥补业务指向缺失。一份明确的直接引用可以独自提供正向依据，不要求为凑数量再找一份重复说明。

对需要联合使用的证据，按以下顺序处理：

1. **回溯原始出处。** 字段名的分词、翻译或归一结果回到同一名称；视图别名和投影回到原表达式；继承、复制或模板生成的说明回到可识别的上游定义。不同对象名不能自动算作不同来源。
2. **比较起决定作用的部分。** 两条材料只是共用目标表和键的身份，可分别支持不同判断；若它们对业务指向的解释都来自同一原始陈述，则把它们合为一份。文本相似但无法判断是否复制时，记为“独立性未知”。
3. **移除当前判断再检查。** 借用其他对象的角色映射时，保留客观的表、列、键身份，移除当前字段对该业务指向的陈述及其派生材料。余下材料必须仍能明确给出同域、同角色、同用途的目标；当前字段本身也必须能够独立识别出待迁移的角色。两边都成立才允许迁移。
4. **保留结论的依据范围。** 独立性只对这项判断有效。已知同源时去重，来源未知时不把它当作独立佐证；若另有一条自足的直接路径，则按那条路径单独裁决。

## 五、有冲突时怎样决定是否连线

按来源字段组一次裁决所有候选，顺序为**结构资格 → 陈述是否适用 → 业务路径是否完整 → 竞争是否消解**。候选展示排序不参与裁决。

| 判断 | 处理 |
| --- | --- |
| 完整目标键、字段配对或类型可比性确定不成立 | 排除该端点组合；命名或注释都不能覆盖结构矛盾。关键属性未知时，有业务线索则保留待判断。 |
| 材料只描述过去、条件性比较或某一外部范围 | 只在其原有范围内使用。历史文字本身不支持当前引用，也不自动否决另一份明确的当前材料。若有适用于当前字段的明确反证，则不能画成无条件本地关系。 |
| 有当前、肯定、限定到端点的直接指向 | 结构通过且无同范围实质冲突时，可消解仅由裸名、近义或词形重合造成的竞争。视图中的直接比较另须确定方向、用途及条件。 |
| 没有直接端点，但有完整业务路径 | 双端描述须同时确定来源的查找意图、目标实体和键用途；角色迁移须通过独立性与作用域判断；常规命名须完整匹配实体与键。完整路径可使异名关系或常规关系进入自动裁决。 |
| 两条适用的明确陈述指向不同目标，或另有合理目标且差异取决于缺失信息 | 保留竞争目标、各自依据及尚缺的区分信息。注释数量、某条路径命中次数、同 schema 和排名第一均不能消解冲突。明确否定当前指向与明确支持当前指向并存时，同样暂缓。 |

证据的强弱取决于它能排除哪一种解释。当前、肯定、限定到端点的陈述可排除只有词形相似的竞争者；同一作用域内两条相反的明确陈述则无法按来源类型强选其一。若一条明确否定只针对某个目标，而该目标仅靠弱命名被召回，则排除该候选并继续评估其余目标。已知条件互不重叠的陈述分开保留；范围重叠或无法区分时，不合并为一条无条件关系。

**自动连线**要求结构通过、至少一条业务路径完整，而且其他合理解释已被排除或已证实不适用于当前范围。**保留候选**用于有业务线索但仍有实质竞争、必要信息未知或条件无法确定的情况。**忽略组合**用于证据只剩通用结构相似，或已证实不相容的情况。单纯缺少可选视图不使任何候选升降级；已知目录缺失且会影响竞争者判断时，暂缓相关裁决。

以上规则处理系统推断。数据库已声明外键与人工确认仍保留各自来源；二者冲突时保留声明事实，并标记相关人工决定需复核。已明确识别的端点在勾选范围外时才记为图外引用。

**联结表的键用途。** 对关系型目录，按原始列标识核对完整复合主键。若来源成员自身单列唯一，仅靠与其他表的键同名仍不足以连线。对于只参与复合主键的成员，逐一核验其完整实体命名、键用途和类型。每个成员都须在同一命名空间内唯一对应另一实体的可信单列键，各成员所指实体应互不相同。若某个成员有竞争目标、缺少类型、带适用范围，或与目录已有指向冲突，则整组不能帮助其他成员消解歧义。通过这项检查后，候选仍进入原有裁决。结构只解释为何此处可以采用同名线索，不增加独立证据的数量。MongoDB 的复合索引不适用这条规则。

## 六、选表、修正与渲染

卡片以原始表名作为标题，表注释、字段名、类型、键标记和字段说明各有自己的排版位置。布局由实际内容高度决定；展开时连线对准字段，收起时对准表头。桌面端按完整表身份记录收起状态，在已有目录快照上重绘，保存 SVG 时使用同一份视图状态。

**MySQL 非空等值。** 驱动分别记录全表键和具有非空适用条件的完整普通唯一键。核查所有键位的原始列、顺序、前缀、表达式和可空性。推断在同一批来源字段的裁决中比较两类目标，按业务证据取舍。有条件目标还需逐列核对完整类型、排序规则及完整配对。能追溯到两端的普通等值视图可提供局部列映射；空安全等值或含这种比较的混合列对不能提供这项证明。条件键对某一字段的局部映射不会成为其他字段的角色锚点。

自动关系及候选通过 `condition.non_null_equality` 标明“所有键位有值且按普通等号比较”；JSON 中缺省该条件的旧关系仍按原有含义读取。SVG 在线上显示条件，桌面预览和 Markdown 解释匹配上限。部分选表时保留条件与可见端点的依据类别，完整库中的其他竞争对象仍受导出范围约束。人工决定不能将条件关系改写为无条件唯一引用。

**条件候选。** 保留 MongoDB 普通部分唯一索引中能够完整解析的标量等值合取。若一个条件无法表示，整个索引不参与这条候选路径。关系型完整唯一键中的布尔限定列只记作未绑定键位。对同一命名空间内的两个实体，至少两个绑定列须在来源的同一索引中共现，按原始列名与目标键逐列配对，且类型没有已知矛盾。若两端都有相应的条件唯一结构，方向无法由此确定。相同端点有不同谓词时暂缓输出。JSON 的 `condition.required_target` 记录目标索引的目录谓词，`condition.unbound_target_columns` 记录未知的绑定。两者均只能形成候选，无法证明应用查询采用了该条件。

结构规则可用一致重命名检验。若同步改写两端标识符并保留列配对、索引和类型，仅依赖结构的判断应保持一致。依赖语言的路径则须明确指出哪些词、角色或注释提供了信息，以及它们消失后应降为候选还是放弃。私有库名、业务表名前缀和源码标注均不进入运行时规则；冻结规则后才读取留出模块的对照结果。

首先得到整个可见目录的关系结果，再按选表截取节点和边。调整勾选时只更新成图范围和布局。刷新目录、改变项目修正或规则版本时，重新计算受影响的裁决。人工映射保存项目及数据库作用域、限定端点、角色和判断所依赖的键或语义；依据变化后标记待复核。

SVG 由 Rust 导出层生成，桌面预览与文件共用节点、线和来源标记。边从引用字段指向目标键，复合关系保留列配对，角色不同的关系分别呈现。图内使用线型和文字标记区分来源，附读取范围、待判断项和图外引用数。完整证据和冲突理由留在预览及可选关系报告中。原有数据字典继续按其既有字段约定输出。[JSON 导出](../crates/dbs-doc/src/json.rs)
